# Behavior Rules — автоматический подбор правил поведения для Codex

> **Codex module #2.** Этот рецепт является частью [установщика AGENTS.md](setup-agents-md.md). Не запускай отдельное интервью и не создавай вторую систему памяти или настроек.

## Задача и границы

Используя уже полученные ответы Q&A (G1–G7, P1–P6) и действующие инструкции, предложить **небольшой**, подходящий пользователю набор правил поведения. Предложение проверяет и записывает существующий установщик AGENTS.md. Пользователь может принять весь набор, изменить конкретное правило или исключить его.

Это **не** механизм технического принуждения: текстовые инструкции не заменяют Codex sandbox, approvals, политики CI, серверные ограничения или отдельные будущие Guardrails. Никаких автоматических проверок при каждом запуске Codex.

## Входные данные и их приоритет

1. Явные текущие ответы пользователя: что хочет, чего не хочет, разрешённые действия и исключения.
2. Уже существующие пользовательские инструкции в активных AGENTS.md/AGENTS.override.md (не перезаписывать без одобрения).
3. Проверенные факты о проекте и текущем режиме работы (репозиторий, документация, конфиги, тестовые команды).
4. Рекомендации пресета из [setup-agents-md.md](setup-agents-md.md), если пользователь ещё не выбрал своё.

Если сведений не хватает, **не придумывай персональные предпочтения**. Примени нейтральное правило либо опусти условное. Задавай один уточняющий вопрос только для противоречия, которое мешает сформировать рабочую конфигурацию. Ответ «не знаю, посоветуй» разрешает рекомендацию, но не выдумывание фактов.

Проверяй только уже доступные ответы текущего диалога или фактически существующие настройки; не заявляй, что помнишь Q&A из другой сессии. При повторной установке сначала восстанавливай применимые установки из текущего AGENTS.md, а не начинай всю анкету заново.

## Каталог правил

Идентификаторы нужны **для проектирования и приёмки**, не вставляй ID, эту таблицу или пояснения в итоговый AGENTS.md.

| ID | Правило (краткая формулировка для генерации) | Когда предлагать | Куда |
| --- | --- | --- | --- |
| CORE-FACTS | Проверяй значимые утверждения по доступным фактам; отделяй факт от гипотезы. | Всем, кроме явного пользовательского исключения | Глобально |
| CORE-EVIDENCE | Называй выполненные проверки и результаты; не выдавай непроверенное за PASSED. | Всем | Глобально |
| CORE-SCOPE | Не изменяй несвязанные компоненты «заодно»; расширение области согласовывай. | Всем | Глобально |
| CORE-ADVICE | Если решение рискованно или есть существенная альтернатива — коротко объясни и предложи выбор; не спорь ради спора. | Всем | Глобально |
| CTX-DOCS | При незнакомом API, спорной версии или недостатке данных сверяй релевантную документацию, а не читай всё заранее. | Когда работа с инструментами/API/изменчивыми фактами актуальна | Глобально или проектно* |
| CTX-DEBUG | При сбоях сначала симптомы, логи и воспроизводимость, затем гипотеза и минимальная проверка. | G1/P1: разработка, DevOps, отладка | Глобально при устойчивой специализации, иначе проектно |
| CTX-INFRA | Не изменяй инфраструктуру/деплой/production без связи с задачей; рискованные изменения согласовывай в рамках выбранной автономности. | G1/P1/P5: эксплуатация, DevOps, production | Проектно для конкретных окружений; глобально — только универсальный принцип |
| CTX-TDD | Применяй Red–Green–Refactor там, где команда действительно работает по TDD. | Только при явном принятом подходе проекта | Проектно |
| CTX-COMMS | Язык, уровень подробности, стиль ответов — по G2/G7; без повторного интервью. | При подтверждённых предпочтениях | Глобально |
| CTX-ASSUMPTIONS | При критичной неопределённости спроси; при обратимой — сделай обозначенное предположение в согласованных пределах. | G3/G4: выбранная модель автономности | Глобально, с проектными исключениями |
| CTX-REGRESSION | Проверяй связанные с изменением тесты; известные регрессии фиксируй в уже принятом владельце состояния, не создавай второй журнал. | P3/P4: есть тестовый процесс, длительный проект | Проектно |

* «Глобально или проектно» определяется **потребностью**, не копированием: если правило универсальное и уже есть глобально, проектная версия нужна лишь для конкретного отличия.

### Правила из оригинала, которые НЕ устанавливает этот модуль

- Обязательные hooks, автоматический стартовый handoff, блокировка опасных команд → **Guardrails / Session Handoff** (отдельные функции).
- Хранение истории ошибок, карта владельцев фактов и очистка документации → **Project Memory / Fact Ownership**.
- Запуск субагентов, отдельные конфиги ролей → **Multi-Agent**.

Их идеи можно упомянуть в объяснении выбора, **но не создавать связанные файлы и не обещать техническое принуждение**.

## Алгоритм без второй анкеты

1. Получи результат аудита и ответы Q&A, которые уже собрал `setup-agents-md.md`. Если первый модуль ещё не настраивался, прочитай существующие инструкции и извлеки только **явно указанные** предпочтения.
2. Рассмотри CORE-FACTS, CORE-EVIDENCE, CORE-SCOPE, CORE-ADVICE. Если эквивалентное правило уже присутствует на действующем уровне, **не дублируй** его. Не восстанавливай правило, от которого пользователь явно отказался.
3. Оцени каждое CTX-правило по таблице. «DevOps» в G1 не означает автоматический TDD, доступ в production или выбор языка программирования. Не добавляй условные правила «на всякий случай».
4. Учти выбранную автономность и стиль общения. Не создавай глобальное правило, противоречащее проектному требованию или реальным ограничениям среды. Если G3 и G6 противоречат друг другу — уточни конкретное противоречие, а не проходи Q&A заново.
5. Выполни **семантическую дедупликацию**: одинаковый смысл под разными словами — одна инструкция, даже если IDs разные. Особенно CORE-EVIDENCE и проверки тестов; CORE-SCOPE и CTX-INFRA; CTX-COMMS и раздел «Общение».
6. Сформируй небольшое число ёмких инструкций, объединяя близкие правила. Не вводи фиксированную норму «все 11 правил» и не растягивай файл ради количества строк. Ссылки на дополнительные документы — только если они реально нужны и существуют.
7. Покажи **один общий предпросмотр вместе с AGENTS.md**: какие правила добавляются, куда и почему; какие не выбраны и почему (кратко, без технического реестра). Пользователь может принять всё, отредактировать или исключить пункты.
8. Передай итог обратно **общему механизму записи** `setup-agents-md.md`: полные тексты, подтверждение, бэкап, один валидный управляемый блок, статическая проверка после изменения. **Не записывай файлы самостоятельно.**

## Разрешение конфликтов

| Ситуация | Решение |
| --- | --- |
| Существующее пользовательское правило совпадает по смыслу | Сохранить его, новый дубль не создавать |
| Глобальное правило противоречит проектному | Показать конфликт, предложить уточнение уровня; не удалять чужую инструкцию |
| Пользователь отказался от рекомендованного правила | Не возвращать правило по умолчанию при следующем запуске; не считать отсутствие разрешением на вмешательство |
| Недостаточно данных для контекстного правила | Пропустить правило или предложить нейтральный вариант, не угадывать |
| Технически опасное желание («обходить approvals») | Пояснить, что AGENTS.md не снимает ограничения; не обещать функциональность |
| Правило уже находится в управляемом блоке с пользовательскими правками | Сравнить смысл и предложить сохранение/правку; никогда не заменять незаметно |
| Есть AGENTS.override.md | Сначала решается активный файл по рецепту AGENTS.md; не писать в неактивный файл |

Не требуется выводить полный diff, если пользователь его не запросил. Но **полный итоговый текст и путь каждого файла** должны быть подтверждены.

## Примеры подбора (не копировать дословно)

**Профиль A:** G1 — DevOps + разработка; G3 — сбалансированно; G4 — проверять; G2 — кратко. Для глобального AGENTS.md предложи коротко CORE-FACTS, CORE-EVIDENCE, CORE-SCOPE/ADVICE, CTX-DEBUG, CTX-COMMS/ASSUMPTIONS. Для проекта с production — отдельное CTX-INFRA, связанное с конкретным окружением. Не добавляй TDD без P4.

**Профиль B:** G1 — аналитика; G3 — осторожно; конкретный проект — отчёты и данные. Предложи CORE-FACTS, CORE-EVIDENCE, CORE-SCOPE, CORE-ADVICE и подтверждённый стиль общения. Не навязывай CI, Docker, debugging, TDD или производственные процессы.

**Повторный запуск:** пользовательская секция уже содержит «не менять несвязанные файлы». Принять её как реализацию CORE-SCOPE, а не дублировать в управляемом блоке.

## Проверка и завершение

Это **проектирование поведения при установке**, не фоновая система контроля. Применяется лёгкая проверка файлов по `setup-agents-md.md`, не новый набор автоматических тестов агента. Проверка прогонов сценариев описана в [tests/behavior-rules-acceptance.md](../tests/behavior-rules-acceptance.md) и выполняется при разработке/приёмке, а не на каждой сессии.

Смежные файлы: [практика AGENTS.md](../practices/01-agents-md.md), [шаблон глобального уровня](../templates/agents/global.md), [шаблон проекта](../templates/agents/project.md).

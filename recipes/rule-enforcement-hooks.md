# Критичное правило обеспечивается механизмом, а не записью

## Как вызвать

Скажите Claude Code обычной фразой: «настрой механизм, который запрещает X и
подсказывает Y», «сделай так, чтобы правило X нельзя было пропустить», «защити
файл Z от случайной правки». Настройка — разовая, дальше механизм работает сам.
Обязательно попросите показать испытания до подключения (см. ниже) — это часть
практики, а не опция.

## Проблема

В CLAUDE.md записано важное правило — заглавными буквами, продублировано в памяти
проекта. Модель его всё равно нарушает.

Это не гипотеза. На зрелом рабочем проекте аудит за несколько недель показал:
правило «такие-то операции — только через выделенный инструмент» соблюдалось
примерно в одном случае из шестидесяти — сотни прямых запусков против единичных
правильных. При этом в том же проекте существовал **hook** — автоматическое
правило-страж, которое Claude Code исполняет до или после действия модели, — и
вот он срабатывал всегда.

Запись в документации — совет, который модель может отклонить в пользу короткого
пути (правило 7 из [`behavior-rules.md`](behavior-rules.md)). Механизм отклонить
нельзя: он исполняется независимо от «решимости модели следовать правилам».

**Формула практики: текст объясняет «почему», механизм обеспечивает «нельзя иначе».**
Оба нужны: механизм без текста непонятен, текст без механизма не работает.

## Какое правило заслуживает механизма

Не «важное» — важность у каждого своя, этот ползунок не даёт границы. Рабочий
критерий — два вопроса о **последствии нарушения**:

1. **Обратимо ли оно?** Испорченный черновик восстанавливается; отправленное
   письмо, затёртый файл пользователя, выполненный платёж — нет.
2. **Остаётся ли оно внутри периметра?** Ошибка в рабочей папке — ваша; утечка
   наружу, действие в чужой системе — уже нет.

Необратимое или выходящее за периметр — кандидат на механизм. Обратимое и
внутреннее — достаточно текста.

Тот же критерий управляет строгостью: для обратимых операций **ложное
срабатывание дороже пропуска** — заблокированная легитимная работа приучает
игнорировать механизм, а пропуск поймается позже. Для необратимых знак меняется:
пропуск не поймается «позже», и граница сдвигается в строгость — лучше лишний
раз спросить.

## Какое правило каким механизмом закрывается

| Тип правила | Механизм | Пример |
|-|-|-|
| «Прочитай это перед началом» | SessionStart hook | доставка ядра эстафеты ([`session-handoff.md`](session-handoff.md)) |
| «Не делай так» | PreToolUse-запрет | запрет опасной операции с инструкцией, что делать вместо |
| «Спроси человека перед действием» | PreToolUse-подтверждение (ask) | необратимая операция ждёт явного «да» оператора |
| «Сделай это после» | PostToolUse-напоминание | чек-лист после правки документа состояния |

**Запрет и подтверждение — разные механизмы, не путайте.** Запрет с обходом
годится для обратимого; для необратимого нужен механизм подтверждения: решение
физически принимает человек, модель не может «выписать себе разрешение».

## Паттерн: запрет с инструкцией и видимым обходом

Плохой hook просто блокирует — оператор упирается в стену. Хороший при блокировке
сообщает три вещи:

1. **Что нарушено** — какое правило и почему существует.
2. **Как сделать правильно** — готовая команда, не отсылка к документации.
3. **Как обойти осознанно** — маркер в команде, пропускающий операцию.

```
ПРАВИЛО: <что защищаем и почему>.
Правильный путь: <готовая команда>.
Осознанный обход: добавьте в команду маркер <слово-маркер>.
```

Честная оговорка о пределе маркера: команду с маркером пишет та же модель,
которую hook ограничивает, — обход технически доступен и ей. Поэтому маркер
работает в паре с **видимостью**: обходы должны быть находимы постфактум
(поиск маркера по журналам сессий; периодический вопрос «покажи все обходы
за неделю»). Обход возможен, но не бесследен — этого достаточно для обратимых
операций. Для необратимых — механизм подтверждения, см. выше.

## ★ Главное: механизм пишется вместе с таблицей испытаний

Прецедент со зрелого проекта: hook блокировал прямой запуск интерпретатора.
Лишний символ в проверке — и hook стал блокировать **имена файлов и пакетов**,
похожие на команду, вплоть до запрета читать файл с таким именем. Ложные
срабатывания на легитимной работе — самый быстрый способ приучить всех
игнорировать механизм.

Поэтому до подключения — таблица испытаний: **минимум по три блокирующих и три
легитимных сценария**, включая пограничные (имена файлов, похожие на команды;
легитимные обращения к своим системам) и обязательную строку **«то же действие
другим инструментом»** — запрет только на один способ модель обойдёт другим
(другой инструмент, другой синтаксис той же операции).

Hook читает описание операции со стандартного ввода, поэтому весь испытательный
стенд — три строки (shell-стенд; на Windows — Git Bash):

```bash
H="scripts/my-hook.sh"
t(){ printf '%s' "$1" | bash "$H" | grep -q '"deny"' && echo "БЛОК   : $2" || echo "пропуск: $2"; }
t '{"tool_name":"Bash","tool_input":{"command":"<опасная команда>"}}'  'ждём БЛОК'
t '{"tool_name":"Bash","tool_input":{"command":"<легитимная команда>"}}' 'ждём пропуск'
```

После подключения — **боевая проверка**: контрольное нарушение (или попросите
Claude Code продемонстрировать блокировку) — механизм сработал, сообщение
читаемо. Без неё «настроенный» hook неотличим от молчащего.

## Границы охвата: настройки не наследуются

Если проект состоит из подпроектов, у каждого своя папка настроек — hook из
корня **не действует** в окне подпроекта
([`parallel-subprojects-shared-memory.md`](parallel-subprojects-shared-memory.md)).
Лечится раскладкой идемпотентным скриптом — с сухим прогоном по умолчанию
(применение отдельным флагом), только по реальным подпроектам (критерий: рядом
есть файл состояния или идентичности), с печатью списка пропущенного, чтобы
отсечение было видно.

## Уровни настройки

**Уровень 0 — правило в CLAUDE.md (по умолчанию).** Зарегистрируйте практику
блоком:

```markdown
<!-- [claude-code-practices v1.10] BEGIN: rule-enforcement-hooks -->
## Правила с механизмом

У критичного правила (необратимое последствие или выход за периметр) должен
быть исполнительный механизм — hook, не только текст.

Попроси меня: «сделай правило X непропускаемым», «защити Y от случайной
правки» — я предложу механизм, покажу таблицу испытаний до подключения
и проведу боевую проверку после.

Подробности — recipes/rule-enforcement-hooks.md.
<!-- [claude-code-practices v1.10] END: rule-enforcement-hooks -->
```

**Уровень 1 — первый механизм по запросу.** Попросите настроить одно правило.
Claude Code обязан: сформулировать точку риска узко, показать таблицу испытаний
до подключения, провести боевую проверку после. Не принимайте «настроено» без
двух последних.

Если механизм ошибочно блокирует легитимную работу — скажите «отключи механизм X»:
блок убирается из настроек, работа продолжается. Отключение — тоже видимое
действие: зафиксируйте причину, чтобы починить проверку, а не забыть механизм.

**Уровень 2 — для разработчиков.** Пишете hooks сами: испытательный стенд выше,
чек-лист ниже, готовые примеры конфигурации — в
[`session-handoff.md`](session-handoff.md) (SessionStart) и
[`guardrail-external.md`](guardrail-external.md) (PreToolUse).

## Как это выглядит в разных практиках

- **Разработчик:** запрет правки сгенерированных файлов; запуск инструментов
  только через обёртки; гардрейл внешних репозиториев
  ([`guardrail-external.md`](guardrail-external.md)).
- **Юрист:** подтверждение перед отправкой итогового документа наружу
  (отправка необратима — сборку можно переделать); чек-лист-напоминание после
  правки шаблона.
- **Бухгалтер/аналитик:** напоминание сверить период после изменения выгрузки;
  защита итогового отчёта от случайной правки агентом — ваши ручные правки
  под защитой, а не под запретом.
- **Консультант-пресейл:** гардрейл на чужие материалы; подтверждение перед
  отправкой клиентского документа.

## Когда НЕ применять

- **Последствие обратимо и внутри периметра** — достаточно текста; hook на всё
  подряд превращает работу в полосу препятствий.
- **Точку риска нельзя сформулировать узко** — широкая проверка даст ложные
  срабатывания, механизм начнут обходить рефлекторно. Сначала сузить.
- **Правило ещё меняется** — механизм фиксирует дисциплину; пока правило не
  устоялось, дешевле править текст.

## Чек-лист внедрения (канонический)

1. Последствие нарушения необратимо или выходит за периметр? Нет — текст, не hook.
2. Точка риска сформулирована узко; проверка — под точку риска, не под тему.
3. Запрет или подтверждение? Необратимое → подтверждение (ask).
4. Таблица испытаний: ≥3 блокирующих + ≥3 легитимных, включая пограничные
   и «то же действие другим инструментом».
5. Прогон до подключения — все вердикты ожидаемые.
6. Подключение; настройки валидны.
7. Боевая проверка: контрольное нарушение остановлено, сообщение читаемо.
8. Есть подпроекты — раскладка скриптом с видимым отсечением служебных каталогов.
9. Правило записано текстом рядом: текст — «почему», механизм — «как».
10. Для запретов с маркером — договорённость о видимости обходов.

## Что делает Claude Code при настройке этой практики

*(Раздел — инструкция для Claude Code на этапе настройки. Пользователю читать
необязательно.)*

При запросе «сделай правило X непропускаемым» — по чек-листу внедрения, вслух:
назвать точку риска и её формулировку, предложить тип механизма (запрет /
подтверждение / напоминание — по обратимости), показать таблицу испытаний
и результат прогона ДО записи в настройки, после записи — боевая проверка
с показом сообщения блокировки.

### Строгие правила (что НЕ делать)

1. **НЕ подключать механизм без показанной оператору таблицы испытаний.**
   Прогон «про себя» не считается — оператор должен видеть сценарии и вердикты.
2. **НЕ ставить запрет с маркером на необратимую операцию.** Необратимое →
   только механизм подтверждения (решение у человека).
3. **НЕ расширять границу проверки «заодно».** Точка риска одна; смежные риски —
   отдельным механизмом с отдельными испытаниями.
4. **НЕ заявлять «настроено» без боевой проверки.** Настроенный, но не
   проверенный механизм неотличим от молчащего.
5. **НЕ чинить ложное срабатывание ослаблением наугад.** Разобрать, какой
   сценарий не был в таблице испытаний, добавить его туда, починить проверку,
   перегнать таблицу.
6. **НЕ трогать существующие механизмы при добавлении нового** — дописывать
   рядом, не заменять (у проекта могут быть свои hooks).

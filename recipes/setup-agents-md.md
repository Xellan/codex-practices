
# Настройка глобального и проектного AGENTS.md для Codex

**Стадия:** первый адаптированный модуль `codex-practices`.  
**Точка входа:** [CODEX-START.md](../CODEX-START.md)  
**Область действия:** только инструкции AGENTS.md, без переноса остальных рецептов Claude Code.

## Результат

Установщик через разговор создаёт или бережно обновляет:
- **Глобальный** `$CODEX_HOME/AGENTS.md` (при отсутствии CODEX_HOME — `~/.codex/AGENTS.md`).
- **Проектный** `AGENTS.md` в подтверждённом корне целевого проекта.
- **Вложенные** AGENTS.md — только при реальной необходимости и отдельном согласии.

Не создавай отдельную базу личных ответов, не сохраняй транскрипт Q&A. Статусы текущих задач и история проекта принадлежат будущей практике памяти.

## Шаг 0. Безопасный аудит (только чтение)

1. Узнай реальный `pwd`, `git rev-parse --show-toplevel` (если проект под Git), значение переменной `CODEX_HOME`. Если переменная задана, **не заменяй** её на `~/.codex`. Проверь, доступен ли `codex` в PATH.
2. Убедись, что целевой проект не перепутан с папкой самого пакета. В режиме «только глобальный» допускается любая отдельная рабочая директория.
3. Проверь глобальные `AGENTS.override.md` / `AGENTS.md`, проектные `AGENTS.override.md` / `AGENTS.md`, а при наличии вложенной цели — инструкции промежуточных директорий от корня Git до cwd.
4. Прочитай `config.toml` **только при необходимости** выяснить `project_doc_max_bytes` и `project_doc_fallback_filenames`. Не исправляй его в рамках этого модуля.
5. Если обнаружен непустой `AGENTS.override.md`, сообщи, что обычный `AGENTS.md` на этом уровне неактивен. Предложи: изменить активный override, оставить его и не трогать базу, либо отдельно обсудить снятие override. **Не удаляй** override автоматически.
6. Если файл существует и является симлинком, это дополнительный риск: не заменяй ссылку молча. Не обходи недоступные файлы, не меняй разрешения без согласия.
7. Покажи сводку текущих инструкций и их фактическую область действия. Сначала спроси область работы: глобальная, проектная или обе (по умолчанию предложи обе).

Согласуй для каждого выбранного уровня: **«использовать существующее как основу»** либо **«настроить с нуля»**. Даже при выборе «с нуля» существующий файл нельзя затирать без показа итогового текста, подтверждения и резервной копии.

## Шаг 1. Q&A: один вопрос за раз

Каждый вопрос должен иметь: короткую цель, **3–5 понятных готовых ответов**, объяснение рекомендуемого варианта, «свой ответ», а где уместно — «несколько вариантов» и «не знаю, порекомендуй». Если человек выбирает пресет, он **может изменить его**. Не требуй описывать незнакомые понятия без объяснения.

**Не задавай все вопросы списком.** Сначала общий контекст, затем только релевантные ветки. Не переспрашивай подтверждённые сведения. При конфликте ответов задай одно предметное уточнение с конкретным примером.

### Глобальная часть — банк вопросов

Это примеры формулировок и ответов, а не жёсткое ограничение содержания. Адаптируй их к человеку.

**G1. Чем ты чаще всего занимаешься?**  
Зачем: чтобы ориентироваться в знакомых задачах, а не навязать стек всем проектам.
1. Разрабатываю приложения и сайты.
2. Занимаюсь серверами, инфраструктурой и автоматизацией.
3. Работаю с данными, аналитикой или исследованиями.
4. Несколько направлений одновременно.
5. Пока учусь или пробую разные задачи.
+ Свой ответ / несколько пунктов.

**G2. Как тебе удобнее получать объяснения?**
1. Короткий ответ и команды.
2. Пошагово, с объяснениями для новичка.
3. Адаптивно: кратко в простом, подробнее в сложном (**рекомендуется**).
4. Сначала вывод, потом обоснование.
+ Свой ответ.

**G3. Насколько самостоятельно агент должен работать?**
1. Осторожно: согласовывать большинство изменений.
2. Сбалансированно: рутину делать самому, рискованные действия обсуждать (**рекомендуется**).
3. Автономно в рамках задачи и технических разрешений.
4. Зависит от проекта — определить на уровне проекта.
+ Свой ответ. Обязательно поясни: текстовая автономность не меняет sandbox, approvals и полномочия инструментов.

**G4. Как Codex должен вести себя при неопределённости?**
1. Проверять доступные данные и спрашивать о критичных пробелах (**рекомендуется**).
2. Чаще задавать уточняющие вопросы.
3. Делать обратимые предположения с явной пометкой и продолжать.
4. Предлагать альтернативы на выбор.
+ Свой ответ. Уточни, как решать противоречия между этим ответом и G3.

**G5. Какие проверки должны быть нормой?**
1. Проверять результат доступными релевантными средствами (**рекомендуется**).
2. Строгие тесты для любых изменений в коде, если существуют.
3. Минимальная проверка для прототипов, тщательная — для важных изменений.
4. Отдельные правила в каждом проекте.
+ Свой ответ. Не записывай в глобальный файл конкретные команды, которых нет во всех проектах.

**G6. Как относиться к опасным операциям?**
1. Согласовывать удаления, секреты, production и необратимые действия (**рекомендуется**).
2. Максимально осторожно: любое изменение внешних систем через подтверждение.
3. По согласованным границам для каждого проекта.
+ Свой ответ. Не предлагай снимать системные ограничения; для реальной безопасности нужна отдельная практика.

**G7. На каком языке общаться?**
1. Русский.
2. Английский.
3. На языке сообщения пользователя.
4. Другой / смешанный режим.
+ Свой ответ.

После G1 допускается один вопрос о **знакомых технологиях**, но лишь если ответ нужен для общения или терминологии. Не превращай знакомые инструменты в универсальное требование использовать их в каждом проекте.

### Проектная часть — банк вопросов

Проектный Q&A начинай после read-only анализа существующих файлов: не спрашивай то, что уже достоверно видно. Пользователю предложи подтвердить вывод.

**P1. Для чего этот проект?**  
Предложи варианты по типу найденного проекта: приложение / инфраструктура / библиотека / документы / другое. Предусмотри произвольное описание.

**P2. Какие технологии здесь используются?**  
Покажи найденные языки/фреймворки как редактируемый вариант, «не знаю — исследуй файлы», «свой ответ». Указывай версии только если они подтверждены.

**P3. Как здесь обычно проверяют изменения?**  
Покажи реально найденные команды из существующей конфигурации и варианты «использовать найденное», «тесты пока не настроены», «укажу вручную». Не выдумывай команды.

**P4. Какие правила изменения проекта важны?**  
Варианты: минимальные правки (**рекомендуется**), согласование архитектурных изменений, TDD если уже принято, собственные конвенции / комбинация.

**P5. Есть ли особые зоны риска?**  
Варианты по контексту: production / миграции БД / пользовательские данные / безопасность / обычный эксперимент / свой ответ. Не требуй секретов и адресов систем.

**P6. Где хранится актуальная документация?**  
Сверь реальные файлы и предложи ссылки. Если документов нет — пропусти, не создавай фиктивных ссылок.

### Пресеты — стартовые ответы, не новые полномочия

Предложи редактируемые пресеты: **Сбалансированный** (по умолчанию), **Осторожный**, **Автономная разработка**. Пресет — сочетание ответов G2–G6; пользователь вправе изменить любой пункт, выбрать свой ответ или комбинацию. «Автономный» не означает обход подтверждений Codex. Профиль выбирается в ходе Q&A, а не навязывается отдельной длинной анкетой.

Не делай большой AGENTS.md ради «полной настройки»: все важные темы обсуждаются, но в итоговый файл попадают лишь устойчивые и действительно полезные инструкции.

## Шаг 2. Генерация текста

Используй [глобальный шаблон](../templates/agents/global.md) и [проектный шаблон](../templates/agents/project.md) как **структурные подсказки**. Не копируй комментарии шаблона, заполнители в квадратных скобках или неиспользуемые секции. Текст должен содержать подтверждённые факты, точные формулировки решений и относительные ссылки на реально существующие проектные файлы.

- Глобально — стиль общения, постоянные рабочие принципы, границы автономности.
- Проектно — описание, стек, конвенции, реальные тестовые команды и указатели на документацию.
- Не дублируй один факт в обоих файлах: проектные инструкции лишь уточняют глобальные.
- Не добавляй секции «текущий статус», журнал событий, историю чатов и секреты.
- Для расширенных навыков, MCP, sandbox и конфигурации Codex оставь будущие отдельные практики.

### Идемпотентное обновление

Управляемые области маркируются точными парами:

- `<!-- codex-practices:agents:global:begin -->` и `<!-- codex-practices:agents:global:end -->`
- `<!-- codex-practices:agents:project:begin -->` и `<!-- codex-practices:agents:project:end -->`

При повторном запуске заменяй **только один валидный согласованный управляемый блок**, не добавляй копию. Не трогай чужие блоки и пользовательские секции. Если метки отсутствуют, предложи аккуратное объединение без смысловых дублей; если метки сломаны или встречаются несколько раз — **остановись** и согласуй ручное исправление. Содержимое до и после управляемого блока сохраняй без изменений.

Режим «с нуля» на существующем файле: покажи, что именно будет заменено и какие пользовательские секции могут исчезнуть; запроси отдельное одобрение полной замены. Без этого переходи к неразрушающему объединению или прекрати установку.

## Шаг 3. Подтверждение и запись

1. Покажи пользователю **полные итоговые тексты** и целевые пути. Diff опционален.
2. Дождись явного согласия на запись **каждого фактически изменяемого файла**.
3. Для каждого существующего файла создай резервную копию рядом с датой и временем в имени; не перезаписывай прошлые бэкапы. Особенно аккуратно с симлинками.
4. Примени правки без изменения остальных файлов и без удаления неизвестных правил. По возможности пиши через временный файл и атомарную замену в том же каталоге. При неудаче не оставляй частично записанный документ и сообщи путь бэкапа.
5. Сохрани исходные пользовательские секции и проверь, что управляемые метки встречаются ровно по одному разу. При повторном запуске неизменный файл не переписывай.
6. Не изменяй `config.toml`, `CLAUDE.md`, системные sandbox-политики и чужую инфраструктуру.

## Шаг 4. Однократная проверка при установке / изменении

**Обязательный лёгкий контроль после записи:** проверить путь, непустой файл, корректность парных маркеров, отсутствие оставшихся заполнителей, сохранность пользовательских частей и превышения лимита инструкций (по умолчанию общий предел 32 КиБ, если конфигурация не меняла его). Учитывать вышестоящие инструкции, а не только один файл. Явные противоречия вынести на обсуждение.

**Опциональный при первичной установке smoke-test:** с согласия пользователя запустить **одну** новую read-only сессию `codex exec --sandbox read-only` в подтверждённой директории и попросить кратко перечислить активные правила. Для глобального файла лучше взять нейтральную директорию без проектных инструкций; для проектного — целевую. Не меняй окружение и не воспринимай пересказ модели как формальную гарантию. Если CLI/авторизация недоступны, сообщи: «проверка загрузки не проводилась».

**Никаких** автоматических тестовых запросов, таймеров, хуков или самопроверок на каждом обычном запуске Codex.

## Приёмка и ошибки

Сценарии: [tests/agents-md-acceptance.md](../tests/agents-md-acceptance.md).

В итоговом сообщении сообщи:
- Какие активные уровни настроены и какие существуют override.
- Какие файлы изменены, какие пользовательские блоки сохранены и куда записаны бэкапы.
- Что статически проверено; запускалась ли новая сессия Codex (и почему нет, если не запускалась).
- Какие вопросы остались неразрешёнными. Не заявляй «установлено и работает», если запись или проверка не удались.

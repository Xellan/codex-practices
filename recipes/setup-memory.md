# Как настроить систему памяти

## Проблема

Claude Code забывает всё после сессии. Решения, найденные вчера, ищутся заново. AI повторяет одни и те же ошибки. Каждая сессия начинается с нуля.

## Три слоя памяти

### Слой 1: MEMORY.md — загружается автоматически

MEMORY.md — файл, который Claude Code автоматически загружает в каждую сессию. Его расположение управляется самим Claude Code, вам не нужно знать точный путь. Лимит ~200 строк — только самое критичное.

**Бюджет размера — критично.** Документированное поведение Claude Code: в сессию загружаются первые **200 строк или первые 25 KB** файла MEMORY.md — что наступит раньше. Хвост обрезается **молча**: последние записи не попадают ни в одну сессию, и об этом ничто не сигнализирует. На зрелом проекте так потерялись 8 записей с действующими поведенческими правилами; обнаружено только аудитом. Для кириллицы в UTF-8 байтовый лимит достигается раньше символьного (~1.5–2 байта на символ). Правило: следить за размером — это машинная проверка, а не глазомер ([`fact-ownership.md`](fact-ownership.md), инвариант размера индекса). При росте порядок такой: сначала **уборка** — убрать отработавшее; индекс всё равно растёт — не резать живые записи и не наращивать ядро новыми блоками, а **делить**: на зрелом проекте индекс перерастает лимит закономерно, и лечится это не ужиманием, а делением на горячее ядро и холодные под-индексы (критерий выбытия и порядок деления — в разделе «Когда индекс перерос лимит» ниже).

**Порядок записей — по критичности, сверху вниз.** Именно поэтому внизу индекса должно лежать то, чью потерю переживём. Вверху — запреты и правила поведения (их потеря — инцидент), внизу — справочные указатели (их потеря — неудобство, переспросить). Если лимит однажды сработает, потеряется справка, а не запрет.

**Запись индекса = указатель, не носитель.** Формат: «что это + когда открывать», одна строка, ориентир ≤200 символов. Детали живут в теле reference-файла. Записи-простыни дублируют тела файлов и устаревают отдельно от них — это анти-паттерн «индекс как второй носитель знаний» (см. [`fact-ownership.md`](fact-ownership.md)).

**Проверка сирот — в обе стороны.** Файл памяти есть, записи в индексе нет → файл никогда не будет найден. Запись есть, файла нет → битая ссылка. Проверять при каждом добавлении файла.

**Что включать:**
- Структура данных проекта (для разработчиков — схема БД; для аналитиков — источники и форматы данных; для менеджеров — структура документов)
- Ключевые решения, которые нельзя нарушать
- Матрица авторитетности данных (какой источник для какого домена)

**Что НЕ включать:**
- Детали реализации (есть в коде)
- Историю изменений (есть в git)
- Подробную документацию (для этого слой 2)
- **Пересказ текущей фазы и статусов** — у них уже есть владелец (эстафета или маркер в CLAUDE.md). Копия в индексе протухнет и будет дезинформировать сессии (см. [`fact-ownership.md`](fact-ownership.md))

**Если проект использует две памяти** (глобальную автопамять Claude Code и локальную папку в проекте) — зафиксируйте критерий разделения письменно. Рабочий вариант: «секреты и доступы — только в локальной памяти проекта, вне профиля пользователя».

**Как начать:** Claude Code сам создаёт и обновляет MEMORY.md. Просто работайте — информация накопится. Можно ускорить:

> Запомни: схема БД состоит из таблиц X, Y, Z. Основные связи: ...

> Запомни: мы используем паттерн X для Y, потому что Z

### Слой 2: Reference files — подтягиваются по запросу

Подробные документы, которые AI читает когда нужно, не забивая контекст постоянно.

**Что это:** reference file — это справочный документ по конкретной теме вашей работы. Например, если вы пишете тексты — это может быть стайлгайд, описание целевой аудитории, примеры удачных текстов. Если разрабатываете — архитектура, паттерны деплоя, решённые проблемы.

**ВАЖНО: не выдумывай reference files за пользователя.** Спроси:

> Reference files — это справочные документы, которые Claude Code подтягивает по необходимости. Они не загружаются в каждую сессию (в отличие от MEMORY.md), а читаются, когда нужны.
>
> Какая справочная информация была бы вам полезна? Например:
> - Описание структуры ваших данных или проекта
> - Стайлгайд или правила оформления
> - Список решённых проблем
> - Словарь терминов вашей области
>
> Расскажите, с чем вы работаете — я предложу подходящие reference files.

Создавай только те reference files, которые пользователь подтвердил. Не генерируй содержимое наугад — спроси, какие данные туда включить, или проанализируй существующие файлы в проекте.

**Где хранить:** в проекте, например `_docs/reference/`. AI найдёт по имени файла, когда понадобится.

**Как упомянуть в MEMORY.md:**
```markdown
## Reference files
- `_docs/reference/[название].md` — [описание, когда читать]
```

### Слой 3: Карточки ловушек — обучение на ошибках

Каждая решённая проблема фиксируется в карточке — подробном файле с причиной и предотвращением. Краткий реестр ловушек хранится в таблице CLAUDE.md (загружается автоматически), подробные карточки — в `_docs/gotchas/`.

**Формат карточки** (`_docs/gotchas/G-NN.md`):

```markdown
# G-NN: [заголовок]
Дата: YYYY-MM-DD | Критичность: высокая/средняя/низкая | Область: [домен]

## Проблема
Что произошло.

## Причина
Почему это произошло.

## Решение
Как починили.

## Предотвращение
Что сделать, чтобы не повторилось.
```

**Протокол пополнения и эскалация** — описаны в `recipes/setup-claude-md.md`, секция «Известные ловушки — главная ценность».

**Если проект использует AI Factory** — навык `/aif-fix` создаёт карточки автоматически в `.ai-factory/patches/`. Формат совместим: те же поля, та же нумерация.

**Где хранить:** `_docs/gotchas/` в проекте (или `.ai-factory/patches/` при использовании AI Factory).

Подробнее об идее карточек ловушек: practices/05-memory.md.

### Память агентов

Агенты могут вести свою персистентную память в reference files — это позволяет накапливать опыт между сессиями.

**Что включать в память агента:**
- Паттерны работы с API (особенности, лимиты, workarounds)
- Решённые проблемы в области ответственности агента
- Особенности окружения (версии, конфиги, зависимости)

**Как ссылаться из файла агента:**
```markdown
## Память
Перед началом работы прочитай: `_docs/reference/agent-[имя]-memory.md`
После завершения — обнови файл новыми находками.
```

**Размер:** 50-150 строк за 2-3 недели активной работы. Если больше — провести ревизию, вынести устаревшее.

**Куда класть запись — три вопроса по порядку** *(«ядро» и «под-индексы» — см. раздел «Когда индекс перерос лимит» ниже; до деления ядро = весь индекс)*:
1. **Должна ли она сработать сама, без запроса?** Да — всегда-активный слой (ядро индекса или CLAUDE.md, см. ниже). Размер и частота здесь не важны: правило, о котором нужно вспомнить, чтобы его прочитать, — не правило.
2. **Если срабатывает по запросу — какова цена того, что оно не сработает?** Внешняя или необратимая (ушло клиенту, попало в отчёт) — всё равно во всегда-активный слой, даже если нужно раз в квартал. Внутренняя (переспросить, потерять полчаса) — в слой по запросу (событийные записи).
3. **Только для попавших в слой по запросу — где именно.** До 5 строк — строкой в индексе (после деления — в под-индексе темы); больше — отдельным файлом, а в индексе указатель на него.

Всегда-активных носителя два, и делятся они по происхождению: правила и конвенции проекта — CLAUDE.md (он их владелец по карте владельцев фактов); уроки, запреты и предпочтения, добытые работой, — ядро индекса памяти.

## Когда индекс перерос лимит: горячее ядро и холодные под-индексы

Под-индексы работают по механизму слоя 2 — читаются по требованию, а не в каждой сессии. Отличие в носителе: под-индекс — файл памяти рядом с индексом (на него распространяются проверка сирот и правила формата записей), а не документ в `_docs/reference/`.

Когда уборка отработавшего сделана, а индекс всё равно за лимитом, совет «режьте записи» — мнимая середина: режешь живые — теряешь накопленные правила, не режешь — хвост обрезается молча, и неизвестно какой. Решение — деление по способу срабатывания записи. Полевая база: на зрелом рабочем проекте деление сжало ядро примерно втрое с сохранением всех действующих правил; наблюдение две недели и месяц эксплуатации после — единичные промахи маршрутизации.

**Горячее ядро** (остаётся в MEMORY.md, в каждой сессии):
- **Всегда-активные записи** — то, что должно сработать само, в момент действия, без запроса: запреты, поведенческие правила, критерии. Правило, о котором нужно вспомнить, чтобы его прочитать, — не правило.
- **Указатели тем** — те же записи-указатели, что и обычные, только ведут не в файл-носитель, а в под-индекс темы. Формат тот же: что это + когда открывать, одна строка. Слова в строке — те, которыми вы эту тему спрашиваете вслух, а не название рубрики: сессия находит тему по совпадению с вашим вопросом. Темы делить так, чтобы их слова не пересекались, — пересечение даёт либо промах, либо лишнюю подгрузку.

**Холодный слой** — тематические под-индексы, каждый собирает указатели одной темы и сводки, к которым возвращаются. Пример деления:

```markdown
# MEMORY.md (горячее ядро)
- НИКОГДА не рассылать наружу без проверки по чек-листу   ← всегда-активное
- Вывод о чужой работе — снимком с датой                  ← всегда-активное
- Документы клиентам: сборка, стили, шаблоны, «как оформить» → docs-index.md
- Окружения: стенды, порядок выкладки                      → ops-index.md
```

Разделение памятей двухслойность не отменяет: секреты и доступы живут там, где сказано правилом разделения выше по рецепту, независимо от слоя.

**Классификация — в момент записи, а не при переполнении.** Новая запись сразу получает ярлык: всегда-активная (в ядро) или событийная — нужная по запросу (в под-индекс темы; темы нет — завести под-индекс и указатель). Носитель этого правила — блок в CLAUDE.md (ниже): классифицирует та сессия, которая пишет, и правило должно быть у неё в контексте, а не в рецепте, который она не читает.

**Правило отбора по цене молчания.** Указатель темы срабатывает по совпадению слов — это вероятностный механизм, гарантии нет и не будет. Поэтому в холодный слой уходит только то, чья цена немого отказа внутренняя (переспросить, потерять время). Всё, что дорого стоит при молчании — внешняя или необратимая цена, — остаётся в ядре независимо от частоты. При сомнении — в ядро: толстое ядро стоит токенов, немой отказ правила стоит дефекта. Противовес осторожности: над ядром стоит проверка размера; она покраснела — спорные записи пересматриваются первыми.

**Из ядра тоже уходят.** Деление даёт разовый запас, а не режим: правила прибывают, и без критерия выбытия ядро снова упрётся в лимит — а делить будет уже нечего. Правило, чей объект исчез (инструмент выведен из работы, процесс закрыт, площадка погашена), переезжает в под-индекс «история решений» — не остаётся в ядре и не удаляется молча.

**Промах маршрутизации — материал, а не досада.** Признак промаха: сессия отвечает на вопрос холодной темы из общих соображений, не открыв под-индекс. Запишите карточку ловушки (слой 3) с той формулировкой вопроса, на которой тема не нашлась, и добавьте её слова в указатель темы. Без этой записи «уточним формулировку» остаётся намерением: промах замечает пользователь, а исправлять надо строку, и между ними нужен канал.

**Проверка после перестройки** — живая, из новой сессии, четыре шага:
1. **Канарейка на правило.** Спровоцируйте ситуацию из **самого нижнего** правила ядра (именно нижнего: проверяется и порядок, и близость к обрезу). Это безопасно — проверяется отказ, а не действие. Правило сработало само, без напоминания?
2. **Канарейка на тему.** Задайте вопрос холодной темы теми словами, какими спросили бы обычно. Правильный ответ содержит факт, который есть только в под-индексе (конкретное имя файла, конкретная договорённость); общее рассуждение без единого такого факта — тема не нашлась, даже если ответ звучит разумно.
3. **Канарейка на лишнее.** Обычный рабочий вопрос не по холодной теме — сессия не должна лезть в чужой под-индекс: лишние подгрузки съедают то, ради чего делили.
4. **Сироты и самопроверка.** В обе стороны и на обоих уровнях: каждый под-индекс упомянут указателем, каждый указатель ведёт в существующий файл, ссылки внутри под-индексов резолвятся. Затем — самопроверка документации: инвариант размера индекса зелёный (тот самый, который перестройку и запустил).

Формула приёмки для неспециалиста: **«задай холодной теме обычный вопрос и покажи в ответе факт, который есть только в под-индексе»**.

**Как это выглядит в разных практиках:**
- **Разработчик:** в ядре — запреты («не трогать прод», «не коммитить без ревью»); в холоде — «архитектура и паттерны», «окружения и стенды».
- **Юрист:** в ядре — «сроки — только из картотеки, снимком с датой»; в холоде — под-индексы по типам дел и шаблонам документов.
- **Бухгалтер/аналитик:** в ядре — «источники цифр — только выгрузки»; в холоде — регламенты периодов, форматы отчётов.
- **Консультант-пресейл:** в ядре — «чужие материалы — через гардрейл», «факты о конкурентах — с датой снятия»; в холоде — досье и история сделок.

**Когда двухслойность НЕ нужна.** Индекс уверенно в лимите — не делите: два слоя дороже одного в сопровождении. Порядок величины тем — единицы, не десятки: пятнадцать под-индексов дают пятнадцать указателей в ядре — экономии нет, а слова тем начинают пересекаться. Типовой случай раннего переполнения — общий индекс на дерево подпроектов ([`parallel-subprojects-shared-memory.md`](parallel-subprojects-shared-memory.md)). Обратный ход существует: слить под-индекс обратно в ядро — перенос строк и удаление указателя, ничего не ломается.

### Блок для CLAUDE.md

Ставится при перестройке (уровень 1: «раздели мне индекс на ядро и под-индексы» — Claude Code проводит деление и ставит блок; четыре шага проверки — из новой сессии, сессия перестройки проверить автозагрузку не может: это был бы запуск вместо выхода). До перестройки блок не нужен.

```markdown
<!-- [claude-code-practices v1.10] BEGIN: memory-two-layer -->
## Память: горячее ядро и холодный слой

Индекс памяти разделён. Новая запись классифицируется В МОМЕНТ ЗАПИСИ,
не при переполнении:
- должна сработать сама, без запроса (запрет, правило, критерий) ИЛИ цена
  её молчания внешняя — в ядро индекса, наверх;
- нужна по запросу темы — в под-индекс темы; темы ещё нет — завести
  под-индекс и указатель на него в ядре;
- правило, чей объект исчез из работы, — в под-индекс «история решений»,
  не оставлять в ядре.
При каждом добавлении файла памяти — проверка сирот в обе стороны.
Индекс подошёл к лимиту автозагрузки — сказать об этом, не резать молча.
<!-- [claude-code-practices v1.10] END: memory-two-layer -->
```

## Как настроить с нуля

### Шаг 1: Начните работать
Claude Code автоматически создаёт директорию памяти. Просто работайте — AI запомнит важное.

### Шаг 2: Явно попросите запомнить ключевое
> Запомни: наш проект использует [стек]. Основные сущности: [список]. Деплой через [способ].

### Шаг 3: Создайте reference files для подробностей
> Создай файл `_docs/reference/ref-architecture.md` с описанием архитектуры проекта на основе текущей кодовой базы.

### Шаг 4: Настройте карточки ловушек
> Создай директорию `_docs/gotchas/` и добавь таблицу «Известные ловушки» в CLAUDE.md. После каждого багфикса — создавай карточку в `_docs/gotchas/G-NN.md`.

### Шаг 5: Поддерживайте актуальность
Периодически:
> Проверь MEMORY.md — актуальна ли информация? Удали устаревшее, добавь новое.

## Авторитетные источники данных

Полезный паттерн для MEMORY.md — указать, откуда AI должен брать информацию по каждому домену:

```markdown
## Авторитетные источники
| Домен | Источник | Не использовать |
|-------|----------|-----------------|
| Схема БД | Миграции / SQL-схема | Код фронтенда |
| UI-компоненты | Код в src/components | Документацию |
| Инфраструктура | docker-compose.yml | Память/старые доки |
| API | Серверные эндпоинты | Хардкод в компонентах |
```
